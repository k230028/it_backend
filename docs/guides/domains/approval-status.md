# 신청서 상태와 작성완료 스탬프

## 상태 코드 (`IT_PTL_APF_PRG_STS_C`, `ApprovalStatus`)

| 코드 | 상수 | 의미 | 결재선 |
| --- | --- | --- | --- |
| `0` | `DRAFTED` | 작성완료. [저장]으로 만든 결재선 없는 신청서 | 없음 |
| `1` | `IN_PROGRESS` | 결재중 | 있음 |
| `2` | `COMPLETED` | 결재완료 | 있음\* |
| `3` | `REJECTED` | 반려 | 있음 |
| `4` | `RECALLED` | 회수 | 있음 |
| `9` | `MANUAL` | 수기등록(편성요청서 반입). 등록자결재요청내용 `수기등록` 표식 | 없음 |

\* 정상 결재 흐름(상신 → 순차 승인)을 거친 결재완료만 해당한다. `ApprovalStamper.stamp(...)`로 편성요청서를 반입해 만든 결재완료·수기등록 받이는 결재선(`TPRMPP_CDECIM`)이 없다 — 실제 결재를 거친 신청서와 구분하기 위해 의도적으로 만들지 않는다.

신청서가 없는 원천은 **임시저장**이다. 상신 대상은 최신 신청서가 `0`인 원천이며, 반려·회수 건은 다시 [저장]해야 상신 대상이 된다.

## 스탬프 규칙 (`ApprovalStamper`)

- `stamp(...)`: 반입 전용. 결재완료 또는 수기등록 상태의 받이를 만든다.
- `stampDrafted(...)`: `ProjectService`·`CostService`가 요청의 `complete=true`일 때 호출한다. 같은 `(원천, 관리번호, 순번)`의 최신 신청서가 `0`이면 제목만 갱신하고, `1`이면 `IllegalStateException`, 그 외에는 새 `0` 신청서를 만든다. 단, 시스템관리자가 `2`(결재완료)·`9`(수기등록) 건을 사후 정정하는 저장은 상태를 바꾸지 않고 기존 신청서를 그대로 유지한다(원장 직접 수정).
- 결재 상신(`ApplicationService.submit`)은 묶음 단위로 새 `1` 신청서를 만든다. `0` 행은 갱신하지 않고 최신 신청서번호 판정으로 자연히 덮인다.

## 쓰기 가드 (`ApprovalWriteGuard`)

원천 개정본 `(원본 테이블, 관리번호, 순번)`의 최신 신청서 상태로 수정·삭제 가능 여부를 판정한다. 관리자 판정은 `OwnershipVerifier.isCurrentUserAdmin()`에 위임한다.

| 최신 신청서 상태 | 일반 사용자 수정 | 시스템관리자 수정 | 삭제(역할 무관) |
| --- | --- | --- | --- |
| 없음(임시저장), `0`, `3`, `4` | 허용 | 허용 | 허용 |
| `1` 결재중 | 차단 | 차단 | 차단 |
| `2` 결재완료, `9` 수기등록 | 차단 | 허용(사후 정정, 상태 유지) | 차단 |

`ProjectService`·`CostService`의 수정·삭제와 `ItBudgetApprovalFacade`의 상신은 이 가드를 원장 잠금 뒤, 동시성 스탬프 대조 전에 통과한다.

## 목록·집계

- `BudgetListVersionScope`: `0`·`1`·`3`·`4` 스코프는 재상신 초안(`LST_YN='N'`)까지 노출한다.
- 결재함 목록(`GET /api/applications`)은 `0`과 `9`(수기등록)를 DB 조건으로 제외한다. 대시보드는 `0`을 제외한다.
- 사이드바 상신 대상 건수(`/pending-count`)는 `apfSts=0`으로 집계한다.
