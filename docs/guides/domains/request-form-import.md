# 편성요청서 반입 가이드

부점이 제출한 편성요청서 엑셀을 원장에 반영하는 `domain.migration.request` 서브시스템의 계약을 정리합니다.
전체 이관 화면(`/admin/migration`)의 편성률 반영은 `domain.migration`의 다른 경로이며 이 문서 범위가 아닙니다.

## 1. 경로와 권한

| 항목      | 값                                                             |
| --------- | -------------------------------------------------------------- |
| API       | `POST /api/admin/migration/requests/dry-run`, `POST /api/admin/migration/requests` |
| 권한      | `SecurityConfig`의 `/api/admin/**` 규칙 + 컨트롤러 `@PreAuthorize("hasRole('ADMIN')")` |
| 요청 형식 | `multipart/form-data` — `files`(파일 목록) + `manifest`(예산연도·파일별 부가 정보·보정값) |
| 화면      | `/admin/migration/requests`                                      |

두 엔드포인트는 같은 `importBatch`를 부르고 `dryRun` 플래그만 다릅니다.
**서버는 dry-run 결과를 보관하지 않습니다.** commit은 클라이언트가 보낸 값을 신뢰하지 않고 전부 다시 검증합니다.

## 2. 처리 흐름

```
RequestFormController
  └─ RequestFormImportService            배치 오케스트레이션 (트랜잭션 없음)
       ├─ WorkbookReader                 시트 분류
       ├─ FormSheetAdapter 구현체        셀 → 생성 요청 조립 + 해석 실패 진단
       │    ├─ CapitalProjectFormAdapter    정보화사업
       │    ├─ RecurringProjectFormAdapter  경상사업
       │    └─ GeneralExpenseFormAdapter    전산업무비(시트 ③)
       ├─ RequestFormValidator           횡단 검증 (필수값·물리 길이·자연키 중복)
       ├─ RequestFormFileImporter        원장 반영 (REQUIRES_NEW — 반영의 원자 단위)
       │    └─ MigrationApprovalStamper     이관 결재 표식
       └─ RequestFormSourceFileArchiver  원본 보관 (commit 경로에서만)
```

### 트랜잭션 경계

- **`RequestFormImportService`에는 트랜잭션을 걸지 않습니다.** 반영의 원자 단위는 `RequestFormFileImporter`의
  `REQUIRES_NEW`이며, 오케스트레이터에 트랜잭션을 걸면 바깥 롤백이 안쪽 커밋과 어긋나 "정상 파일만 반영"이 성립하지 않습니다.
- 조직·비목 인덱스(`OrgIdentityResolver.snapshot()`, `IoeHierarchyIndex.snapshot()`)는 배치 시작에 한 번 만들어
  모든 파일이 공유합니다. 파일마다 만들면 수백 회 전량 조회가 됩니다.
- 부서 폴더가 `부서명(부서코드)` 형식이면 CORGNI 등록 여부와 관계없이 폴더의 코드·이름을 사용합니다. 조직 개편 시점에
  제출 폴더와 조직 마스터 반영 시점이 어긋나도 폴더에 명시된 식별자를 잃지 않습니다. 코드 없이 이름만 있는 폴더는 기존처럼
  CORGNI 이름 인덱스로 해석합니다.
- **편성행(`BBUGTM`)은 만들지 않습니다.** `BudgetRateApplicationService.applyItemRates`가 연도 전량을 논리삭제한 뒤
  재삽입하는 구조라, 파일마다 부르면 앞서 반입한 편성행이 전부 사라집니다. 편성은 반입을 마친 뒤 예산작업 화면에서 한 번에 적용합니다.
- 편성요청서로 생성한 프로젝트의 대표 상태(`BPROJA.IT_PTL_STS_TC`)는 **`10`(예산편성 요청 결재완료(migration))**으로
  기록합니다. 일반 프로젝트 생성의 작성중 상태 `01`과 구분하며, 단계 키는 프로젝트 관리번호 자신을 사용합니다.
- `RequestFormSourceFileArchiver`는 **예외를 밖으로 던지지 않습니다.** 원장 반영이 이미 커밋된 뒤에 실행되므로,
  보관 실패로 반입 전체를 실패로 돌리면 되돌릴 수 없는 원장이 남은 채 사용자에게 실패로 보입니다.

## 3. 진단 심각도

심각도는 `RequestFormDiagnosticCode` **enum 상수에 붙어 있습니다.** 호출부가 정하지 않습니다 — 호출부에서 정하게 하면
같은 코드가 파일마다 다른 심각도로 나가 사용자가 기준을 잡을 수 없습니다.

| 심각도    | 결과                | 코드                                                                                                                                    |
| --------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `BLOCKER` | 그 파일을 반영하지 않음 | `FILE_UNREADABLE`, `ANCHOR_NOT_FOUND`, `ORG_UNRESOLVED`, `ORG_AMBIGUOUS`, `USER_UNRESOLVED`, `USER_AMBIGUOUS`, `CODE_UNRESOLVED`, `CODE_AMBIGUOUS`, `REQUIRED_MISSING`, `DUPLICATE_EXISTS`, `LENGTH_EXCEEDED` |
| `WARNING` | 반영함              | `SHEET_NOT_FOUND`, `CODE_DEFAULTED`, `UNIT_UNCERTAIN`, `AMOUNT_MISMATCH`, `OPTIONAL_MISSING`, `SUBSTITUTE_DROPPED`, `DATE_UNPARSEABLE`      |

파일 상태(`RequestFormDto.FileStatus`)는 넷입니다.

| 상태      | 뜻                                                       |
| --------- | -------------------------------------------------------- |
| `APPLIED` | 원장에 반영됨                                             |
| `BLOCKED` | BLOCKER 진단이 남아 반영하지 않음                          |
| `FAILED`  | 예상하지 못한 오류로 실패 (해당 파일만 롤백)               |
| `SKIPPED` | 반입 대상 시트가 없어 건너뜀 — **실패가 아님**             |

`SKIPPED`가 실패가 아닌 이유: 부점 폴더 아래에 팀·사업 폴더가 더 있는 구조에서는 편성요청서가 아닌 엑셀이 함께 올라오는 것이
정상입니다. 그것을 실패로 부르면 관리자가 고칠 수 없는 붉은 줄이 결과 표를 채웁니다. 차단 건수·반영 건수 어디에도 세지 않습니다.

### 코드를 고를 때 헷갈리는 짝

- `CODE_AMBIGUOUS`(BLOCKER)는 **아무 코드도 못 정한** 상태입니다. `CODE_DEFAULTED`(WARNING)는 **합리적인 기본값을
  정했지만** 다른 선택지가 있는 상태입니다. 둘을 같은 BLOCKER로 묶으면 기본값을 제시하는 의미가 사라져, 개발비·기타무형자산
  품목이 있는 파일이 사람이 매번 같은 값을 다시 고르기 전까지 전부 차단됩니다.
- 해석 실패 진단은 **어댑터**가 냅니다. 어댑터는 셀 좌표를 아는 대신 DB 상태나 배치 전체를 보지 못합니다. 필수값·물리 길이·
  자연키 중복처럼 조립 결과를 놓고 봐야 하는 것만 `RequestFormValidator`가 봅니다.
- 공란은 진단 대상이 아닙니다. `USER_UNRESOLVED`는 **값이 있는데** 해석에 실패한 경우입니다.

### 진단을 내기 전에 걸러 내는 행

시트 ③의 **집계 행**은 원장 행이 아니므로 `GeneralExpenseRowReader`가 읽는 단계에서 버립니다. 읽어 두고 진단만 면제하면
비목·통화가 빈 전산업무비가 원장에 생기고, 차단을 사람이 풀어 주면 같은 금액이 두 번 반입됩니다. 판정 기준은 둘입니다.

- 비목명·세부비목·계약명 중 하나가 `계`·`소계`·`합계`·`총계`·`총합계`이거나 뒤에 괄호로 산식·설명이 붙은 행. 비목명이나 계약명으로 쓰일 수 있는 말이 아니라
  오검출 여지가 없습니다.
- **통화 구분 칸의 좌우(계약명·월간)가 모두 빈 행.** 계약 한 건을 적은 행이 아니라 연간 칸에 금액만 얹은 집계 행이거나 표를
  늘리다 만 잔재입니다. 계약명을 위 행과 세로 병합한 정상 행은 `SheetAnchorScanner.text`가 병합 좌상단 값으로 풀어 주므로
  여기 걸리지 않습니다.

버린 행의 비목명은 forward-fill로도 이어받지 않습니다. `계`를 물려주면 그 아래 행의 비목까지 함께 어긋납니다.

### 한 행에 여러 건을 묶어 적은 행

부점은 같은 비목의 계약 여러 건을 행마다 적지 않고 **한 행 안에 번호로** 몰아 적습니다(`① … ② … ③ …` 또는 `1. … 2. … 3. …`).
`FormEnumeration`이 이 행을 항목 수만큼 나누고, 시트 ③ 리더가 **항목마다 전산업무비 한 건**을 만듭니다. 한 건으로 합치지 않는
이유는 계약명·상대처·계약구분이 항목마다 다르기 때문입니다 — 실측 제출본에 ①만 신규이고 ②③은 계속인 행이 있어, 합치면 계약구분을
결정할 수 없고 계약명·상대처가 세 건의 글자를 이어 붙인 덩어리가 됩니다. 전산업무비 원장은 계약 단위입니다.

- 번호 체계는 **계약명 칸을 기준으로** 정합니다. 다른 칸은 위치가 아니라 **번호로** 맞추므로, 비고에 `②`만 적혀 있으면 그 값은
  두 번째 항목에만 붙습니다.
- 원문자(`①`)는 줄 중간에 나와도 번호로 봅니다(실측 제출본에 `② 73,723③ 8,065`처럼 줄바꿈이 빠진 칸이 있습니다). 아라비아
  숫자(`1.`)는 **줄머리에서만** 봅니다 — 줄 중간까지 보면 `28.6백만원`이나 `3.5%`가 번호로 잡혀 정상 행이 쪼개집니다.
- 번호가 없는 칸(통화 구분·비목명 등)은 행 전체에 걸린 값이라 모든 항목이 함께 씁니다.
- 정보보호 여부가 `① X ② X ③ X`로 적혀 해석에 실패하던 것은 이 분해로 풀립니다. 나뉜 뒤에는 항목마다 `X` 한 글자라
  `FormLexicon.toYn`이 그대로 `N`으로 접습니다.

**보정값은 엑셀 행 단위입니다.** 나뉜 항목들이 같은 `excelRow`를 공유하므로 미리보기에서 고른 통화·비목은 그 행의 모든 항목에
함께 걸립니다. 이 칸들은 원래 행 전체에 하나씩만 적히므로 실사용에서 갈릴 일이 없습니다.

### 한 파일에 같은 종류의 요청서가 여러 장인 경우

같은 워크북에 `1-1`·`1-2`·`일반관리비` 시트를 복제해 여러 요청서를 담은 제출본도 있습니다. `WorkbookReader.classifyGroups`는
종류별 n번째 시트를 같은 n번째 요청서 묶음으로 짝지으며, `RequestFormImportService`는 모든 묶음의 변환 결과를 합칩니다. 따라서
먼저 나온 시트 한 장만 인식해 나머지 요청서를 누락하지 않습니다.

정보보호 여부는 `X`·`Ⅹ`·`✕`·`×` 등을 `N`으로 읽습니다. 정의되지 않은 표기는 일반 항목(`N`)으로 기본 처리하고
`CODE_DEFAULTED` 경고를 남기므로 파일 반입을 차단하지 않습니다.

정보화사업의 사업설명·현황(각 1,000자), 필요성·향후계획(각 300자), 사업범위(600자), 기대효과·미추진시 문제점(각
4,000자), 추진경과(2,000자)가 저장 컬럼 한도를 넘으면 허용 길이까지만 반입하고 `TEXT_TRUNCATED` 경고를 남깁니다. 원문 길이
초과만으로 파일 전체를 차단하지 않습니다.

### 금액 칸의 단위·통화 표기

금액 칸에 숫자만 적혀 있지 않습니다 — `2,122백만원`·`41,868,816원`·`20,000USD (원화기준 28.6백만원)` 같은 표기가 실측
제출본에 그대로 들어 있습니다. `FormAmount`가 괄호 주석과 통화코드를 떼고 숫자를 읽습니다. 이 처리가 없으면 그 행은 **금액이
없는 것으로 버려져** 사업 소요금액이 0원이 되거나 `금액이 비어 있습니다` 차단이 납니다.

단위 표기(`원`·`천원`·`백만원`)는 버리지 않고 **그 칸의 단위로 채택하며, 시트 머리말이나 어댑터 기본 단위보다 우선합니다.**
실측 제출본 하나는 머리말이 `단위: 천원`인데 한 칸만 `41,868,816원`이라, 단위를 버리고 시트 배수를 곱하면 금액이 1,000배가
됩니다. 같은 이유로 단위를 밝힌 행은 시트 단위 추정 표본과 단위 오타 보정(1/1000) 대상에서도 뺍니다.

소요자원 표(1-2·②)에서 **소요예산 칸이 비고 단가만 있으면 `수량 × 단가`로 채웁니다**(수량이 없으면 1건). 그대로 두면 그 행이
버려져 사업 소요금액이 0원이 됩니다. 산출값이 실제와 어긋나면 1-1 선언 금액과 1-2 합계를 맞대보는 기존 대사가
`AMOUNT_MISMATCH` 경고로 잡습니다.

정보화사업의 사업 단위 금액은 1-1을 기준으로 `총소요금액 = 전체기간`, `예정금액 = 기준연도 이후`, `기지급금액 = 전체기간 −
현재 요청금액 − 예정금액`으로 저장합니다. 현재 요청금액과 1-2 품목 합계의 상대 오차(`|요청−품목| / 품목`)가 **3% 미만**이면
현재 요청금액만 품목 합계로 보정하고 기지급금액을 다시 계산합니다. 3% 이상이면 자동 보정하지 않고, 요청금액·품목 합계·예정금액·
기지급금액을 구분한 `AMOUNT_MISMATCH` 경고를 남겨 사람이 확인할 수 있게 합니다. 3%는 배타 기준이므로 정확히 3%인 경우도 경고
대상입니다.

사업 생성 과정에서 품목 합계 스냅샷이 먼저 계산되더라도, 반입 마지막 단계에서 위 1-1 금액 스냅샷을 다시 기록합니다. 따라서 품목에
향후 금액이 별도로 적혀 있지 않아도 1-1의 기준연도 이후 예산이 `MPL_AMT`에서 누락되지 않습니다.

### 1-2 일반관리비 블록과 시트 ③의 중복

시트 1-2는 자본예산 블록 아래에 일반관리비 블록이 이어집니다. **두 블록 모두 그 사업의 `BITEMM`으로 담습니다** — 양식이
`정보화사업에 포함된 일반관리비는 1-1·1-2 시트에 작성`이라고 안내하고, 1-1 요약표의 `'26년도 합계`도 자본예산과 일반관리비를
합한 값이라, 일반관리비를 빼면 그 사업의 소요금액이 1-1 선언액과 어긋납니다.

당해 기준액은 **자본 합계에서 시작해 일반관리비 행을 시트 순서대로 하나씩 더해 가며** 1-1 `'26년도 합계`와 맞는 지점으로 정합니다
(`CapitalProjectFormAdapter.closestCurrentBasis`). 일반관리비 전액을 당해분으로 보지 않는 이유는 실측 제출본의 1-2
일반관리비가 익년 이후 계약분까지 담은 연간 금액이기 때문입니다(자금운용실: `'27년 유지보수료` 6,309,600원 포함). 이 기준액으로
기지급금액을 계산하고 1-1 배수도 역추정합니다.

같은 계약을 시트 ③에도 옮겨 적은 제출본이 있습니다. **중복은 시트 ③ 쪽에서 거릅니다**(`GeneralExpenseFormAdapter`). 1-2는
사업 품목의 원천이라 거기서 빼면 위 대사가 무너지지만, 시트 ③은 사업에 매이지 않는 전산업무비 원장이라 한 건이 빠져도 다른 금액이
흔들리지 않습니다. 판정 기준은 **계약명 = 1-2 항목명**(공백 제거 후 비교)이며, 금액은 보지 않습니다 — 시트 ③은 배수가 확정되기
전이고 1-2 일반관리비는 연간 금액이라 같은 계약이라도 두 숫자가 어긋나는 것이 정상입니다. 버린 행은 `SUBSTITUTE_DROPPED`
경고로 남겨, 1-1이 빈 껍데기라 정보화사업이 만들어지지 않은 파일에서도 그 금액이 조용히 사라지지 않게 합니다. 대조 상대는
`WorkbookReader.classifyGroups`가 짝지은 같은 순번의 1-2뿐이라, 1-2가 여러 장인데 시트 ③이 한 장인 워크북에서는 두 번째
이후 사업과는 대조하지 않습니다.

### BLOCKER의 적용 범위

한 파일에 정보화사업·경상사업·일반관리비 시트가 함께 있어도 BLOCKER는 해당 업무 영역에만 적용합니다. 정보화사업의 품목 비목이
미확정이면 정보화사업만 제외하고, 경상사업명이 비었으면 경상사업만 제외하며, 정상 일반관리비는 계속 반입합니다. 시트가 없는 파일
단위 BLOCKER는 어느 영역에도 안전하게 귀속할 수 없으므로 파일 전체를 차단합니다.

부분 반입 파일은 반영 가능한 상태로 돌려주되 BLOCKER 진단을 삭제하거나 WARNING으로 낮추지 않습니다. 화면의 진단 컬럼과 유형별
차단 건수에는 원래 BLOCKER를 그대로 표시해 무엇이 제외되었는지 확인할 수 있게 합니다.

## 4. 공통코드 조회 기준

이관 조회는 `MigrationIoeCatalogReader`가 담당합니다. **조회 기준을 저장 경로와 맞추는 것이 이 리더의 규칙입니다.**

| 대상                            | 조회                                       | 유효일자 |
| ------------------------------- | ------------------------------------------ | -------- |
| 환율(`xcrByCurrency`)           | `findByCIdWithValidDate`                   | 본다     |
| 통화 후보(`currencyCandidates`) | `findByCIdWithValidDate`                   | 본다     |
| 그 밖의 코드·후보               | `findByCIdAndDelYn`                        | 보지 않음 |

- 환율과 통화 후보가 유효일자를 보는 이유: 저장 경로(`CostService.createCost` → `XcrLookupService.resolveXcr`)가
  `findByCIdAndCdvaWithValidDate`로 **유효일자 재조회**를 하고 없으면 `IllegalStateException`으로 롤백합니다.
  조회 기준이 어긋나면 유효기간이 닫힌 통화가 선택지에 떠서 사전검증은 통과하고 반영에서 그 파일만 실패합니다.
- 통화 후보에서 **환율값 파싱 가능 여부까지 거르지 않습니다.** `resolveXcr`이 `KRW`를 조회 없이 통과시키므로,
  거르면 가장 흔한 통화가 선택지에서 빠집니다.
- 그 밖의 코드가 유효일자를 보지 않는 이유: 저장 경로가 유효일자로 재조회하지 않아 기준을 맞출 상대가 없고,
  여기서만 좁히면 원장에 이미 쓰여 있는 값이 이관에서만 미해석으로 떨어집니다.

## 5. 원본 보관과 열람 권한

반입 원본은 전용 테이블 없이 공통첨부파일(`TPRMPP_CFILEM`)을 재사용합니다.
`RequestFormSourceFileArchiver.APG_FL_KD_NM = "편성요청서반입"`이 이 파일 종류의 단일 출처입니다.

- **보관 단위**는 사업 보관 그룹과 파일 처리에서 확정한 **부서코드의 조합**입니다. 사업 폴더가 같아도 검증 코드가 다르거나,
  검증 코드가 같아도 사업 폴더가 다르면 파일과 신청서번호를 섞지 않습니다.
- **디스크 기록은 파일당 1회**이고, 두 번째 연결부터는 물리 경로를 공유하는 메타행만 추가합니다
  (`FileService.linkExistingFile`). 그래서 APPLIED 파일 1건이 신청서 수만큼 메타행을 만듭니다.
- 보관은 **commit 경로에서만** 실행합니다. dry-run은 원장을 만들지 않으므로 보관할 대상도 없습니다.
- `archiveOnly=true`인 항목은 원장 파싱 없이 같은 폴더의 반입 원본으로만 보관합니다.

### 열람 권한

`RequestFormFileReadAuthorizer`가 판정합니다. 파일의 부모(`APG_FL_LNK_CTZ_NM`)는 반입받은 **신청서번호**이므로, 그 신청서가 가리키는
원장(`TPRMPP_CAPPLA` → `BPROJM`/`BCOSTM`)의 주관부서를 사용자 부서와 비교합니다.

- 관리자 → 허용
- 연결된 **활성** 원장의 주관부서가 사용자 부서와 같으면 허용
- 그 밖(미인증, 부모 없음, 원장 없음, 매핑·원장이 논리 삭제됨) → 거부

매핑과 원장 모두 `DEL_YN='N'`인 것만 봅니다. 권한 판정은 실패 시 거부(fail closed)여야 하므로, 논리 삭제나 재매핑 뒤에도
구 부서 사용자가 원본을 계속 열람하는 경로를 남기지 않습니다.

판정은 `(APG_FL_KD_NM, APG_FL_LNK_CTZ_NM, user)`의 순수 함수라는 `FileReadAuthorizer`의 불변식을 지킵니다 — 개별 파일의 다른 속성을
보지 않습니다. 업로드 저장경로 정화와 다운로드 경로 검증은 [파일 보안](../security/file-security.md)을 따릅니다.

## 6. 금액 단위

시트 ③(전산업무비)의 금액 기재 단위는 원/천원/백만원 중 하나입니다. 결정 순서는 다음과 같습니다.

1. 사용자가 manifest에 지정한 `generalExpenseUnit`
2. 시트가 명시한 단위 표기(`단위: 천원` 등)
3. 원화 행 금액 크기로 추정 → `UNIT_UNCERTAIN` 경고로 확인 요청

**전 행의 통화가 확정되었고 그중 원화가 하나도 없으면 경고를 내지 않습니다.** 이 배수는 원화 행에만 걸리고 외화 행은 통화 기본
단위 그대로 `FC_AMT`로 가므로, 원화 행이 없는 시트(국외 점포 실측)에서는 어떤 값을 골라도 결과가 같습니다.

반대로 **미해석 행이 하나라도 남아 있으면 경고를 냅니다.** 그 행은 사람이 통화를 고치면 원화가 될 수 있어 "원화 행 없음"이
성립하지 않습니다. 이 구분을 빼면 통화 칸이 빈 제출본에서 사전검증에 단위 확인이 뜨지 않고, 보정 후 반영에서 배수가 확인 없이
추정 적용됩니다 — 금액이 1,000배 틀린 채 원장에 들어갈 수 있습니다.

## 7. 국문·영문 대조표

해외점포는 같은 양식을 영문으로 번역해 제출합니다. 시트명은 국문 그대로라 시트 판별은 영향받지 않지만 라벨·비목명이 전부
영문이라 국문 기준 매칭이 빗나갑니다. `FormLexicon`이 대조표를 한곳에 모아 새 표기가 나타났을 때 상수 한 줄 추가로 끝나게 합니다.

**미식별 어휘를 추측해 매핑하지 않습니다.** 원문을 그대로 넘겨 미해석 진단(`CODE_UNRESOLVED`)이 나게 하고 미리보기에서
사람이 고르게 합니다. 현재 표는 런던지점 제출본 1건에서 뽑았으므로, 다른 해외점포(시드니·뉴욕·도쿄 등) 제출본이 들어오면
미해석으로 남은 어휘를 수집해 추가합니다.

### 계약구분은 기호와 낱말을 모두 받습니다

시트 ③의 `계속`·`신규` 열에 표시 기호(`O`·`√`) 대신 **열 이름을 낱말로** 적어 내는 부점이 있습니다. 못 읽으면 두 열이 모두 미표시가
되어 계약구분이 진단 한 줄 없이 `해당없음`으로 떨어집니다. **자기 열의 이름만** 표시로 봅니다 — 계속 열의 `신규`까지 세면 두 열이
동시에 켜져 판정이 무너지고, 열을 잘못 짚은 것인지 값을 잘못 적은 것인지 구분할 수 없습니다.

### 담당자 이름은 사번 형태로만 사번으로 봅니다

담당자 컬럼(`USID`·`TLR_USID`·`CGPR_ID`)은 사번 **또는** 이름을 담습니다. 둘을 가르는 규칙은 `UserNameResolver`에 있고,
**사번 형태 = ASCII 영숫자만 쓰고 숫자를 하나 이상 포함**입니다(실측 `TPRMPP_CUSERI.ENO`는 `K140024` 형태 7자, 공백 없음).

"ASCII이면 사번"으로 보면 **영문 성명이 사번으로 오인됩니다** — 해외 점포 제출본의 담당자(`Luke Buckingham-Brown`)가 이름
자리에 뜨지 않고 행번 자리에만 남고, 조회 화면에는 눌러도 결과가 없는 사번 링크가 걸립니다. 프론트 `EmployeeLink.vue`가 링크
여부를 같은 규칙으로 판정하므로 **두 곳을 함께 고쳐야** 합니다 — 어긋나면 서버가 이름으로 본 값에 링크가 남습니다.

### 전결권자 대조표는 따로 둡니다

1-1의 `전결권자` 칸은 자유 기재라 부점이 직제상 직명이 아니라 소관 직책을 적습니다(`부서장`→`부점장`,
`정보보호최고책임자`→`지역본부장`, `수석부행장`→`전무이사`, `○○본부장`→`지역본부장`). 이 대조표는 체크박스 대조표
(`canonicalOptionName`)와 **섞지 않습니다** — `부서장`은 최종보고(`IT_PTL_RPR_STS_TC`)에서는 그 자체가 코드값명이지만
전결권에서는 `부점장`이라, 한 맵에 넣으면 최종보고 체크박스가 조용히 어긋납니다. 전결권 전용 입구는
`FormLexicon.canonicalEdrtName`입니다.

직명 뒤에 검토 상태를 붙인 `이사회(예상)`·`전무이사 (예상)`은 끝의 `(예상)`을 제거한 뒤 전결권 코드와 대조합니다.
또한 사업명 칸이 `해당 없음`·`해당사항 없음`으로 끝나는 정보화·경상사업 시트는 미작성 양식으로 보고 진단 없이 건너뜁니다.

## 8. 국외 부점의 비목

부점 소속은 **부서코드 앞자리**로 가릅니다 — `9**`가 국외 점포입니다(`FormAdapterContext.foreignBranch`). 통화로 가르지
않는 이유는 국내 부점도 외화 계약을 맺고 국외 점포도 원화 행을 적어 내기 때문입니다.

국외 부점의 **전산제비**는 세부를 나누지 않고 `국외전산제비`(계정 240-9100) 한 항목으로 편성합니다. 중분류만 적힌 행이
국외 세부 3종(국외회선사용료·국외유지보수료·국외전산기타제비)에 걸려 늘 `CODE_AMBIGUOUS`로 차단되던 자리라,
`IoeHierarchyIndex`가 국외일 때만 이 값을 기본값으로 정하고 나머지를 대안 후보로 함께 줍니다(`CODE_DEFAULTED`).

기본값을 **코드값이 아니라 코드값명**으로 적는 이유는 같은 비목의 코드값(`CDVA_ID`)이 환경마다 다를 수 있기 때문입니다.
자본예산 계열의 `DEFAULT_CODE_BY_GROUP`만 코드값이 고정되어 있어 코드로 적습니다.
